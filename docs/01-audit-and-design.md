# AUTO CREW — аудит и проектирование (этапы 1–2)

Статус: **черновик для согласования**. Кода игры ещё нет. После согласования этого документа начинается этап 3 (игровой MVP).

---

## 0. Коротко

- Репозитория AUTO CREW нет: в аккаунте `staffvpn` есть только `brewcrew`, `bigunderfm`, `Wolso` и другие проекты. Рабочая папка была пустой. Значит, проект создаётся с нуля, и ломать нечего.
- Brew Crew хорош как образец интеграции с Telegram: проверка initData, вебхук бота, канал, Stars, админка в боте. **Игровую логику оттуда брать нельзя по архитектурной причине**: в Brew Crew вся экономика считается на клиенте и хранится в `localStorage`/`CloudStorage`, а сервер принимает от клиента `money`, `earned`, `level` на веру. Для AUTO CREW требование обратное: деньги, склад, сотрудники и машины считает только сервер.
- Предлагаемая основа: **Cloudflare Worker со статическими ассетами + D1 + Cron Triggers**, TypeScript, общий модуль игровых правил для сервера и клиента. R2 и KV не нужны на старте.
- Экономика рассчитана моделью (`tools/balance_sim.py`, `tools/balance_tune.py`), а не придумана. Активный игрок доходит до первого механика на 9-й день, до автосервиса на 51-й, до перепродажи машин на 80-й, до холдинга на 211-й, до AUTO CREW PRIME примерно за 10–11 месяцев.

## 1. Аудит

### 1.1. Что есть

| Объект | Состояние |
|---|---|
| Репозиторий AUTO CREW | Отсутствует |
| Бот, канал, домен AUTO CREW | Неизвестно, нужно уточнить (см. раздел 9) |
| Референс `staffvpn/brewcrew` | 38 файлов: `index.html` (8 558 строк, вся игра), `functions/` (Cloudflare Pages Functions, ~1 200 строк), D1 + KV, картинки |

### 1.2. Как устроен Brew Crew

- **Клиент**: один `index.html` без сборки, canvas + DOM, спрайт-лист `sprites.png`. Весь симулятор (гости, персонал, финансы, события) работает в браузере.
- **Сохранение**: `localStorage` и дублирование в `Telegram.WebApp.CloudStorage` кусками. Сервер состояния игры не хранит.
- **Сервер** (Pages Functions):
  - `_lib.js`: `verifyInitData` (корректная HMAC-проверка подписи Telegram с ограничением возраста), `tgApi`, каталог покупок за Stars, напоминания, рефералы;
  - `/api/track`: раз в минуту клиент присылает статистику (`money`, `earned`, `level`), сервер пишет её в `players` как есть;
  - `/tg/webhook`: `/start`, `/admin`, оплата Stars (`pre_checkout_query`, `successful_payment` с `INSERT OR IGNORE` по `charge_id`, то есть идемпотентно);
  - `_channel.js`: версия и changelog захардкожены константами (`VERSION = '8.2'`); `channelTick` публикует пост о версии один раз (ключ `ver_8.2` в таблице `posts`);
  - `admin_ops`: очередь команд админа, которые клиент забирает и подтверждает через `/api/ack`.
- **Крон**: «ленивый» (фоном из `/api/track` и вебхука) плюс `GET /api/cron?key=…` для внешнего планировщика. У Pages Functions нет своих Cron Triggers.
- **База**: схема и миграции в репозитории отсутствуют, таблицы создавались вручную.

### 1.3. Что берём

| Что | Как используем |
|---|---|
| `verifyInitData` | Переносим почти без изменений, добавляем проверку на каждый игровой запрос |
| Вебхук с `X-Telegram-Bot-Api-Secret-Token`, `/tg/setup` | Тот же подход |
| Идемпотентная запись платежей по `charge_id` | Обобщаем на все игровые операции (раздел 2.3) |
| Публикация в канал с сохранением `message_id` | Берём идею, но делаем через очередь черновиков с модерацией |
| Список админов | Переносим в таблицу `admins`, без захардкоженных ID в коде |
| `_headers` с `no-cache` для HTML | Берём, плюс хешированные имена ассетов |

### 1.4. Что не берём и почему

| Проблема в референсе | Последствие | Решение в AUTO CREW |
|---|---|---|
| Экономика на клиенте, сервер верит присланным числам | Деньги правятся через DevTools; рейтинг и награды подделываются | Сервер — единственный источник истины, клиент только отображает и отправляет команды |
| Сохранение в `localStorage`/`CloudStorage` | Потеря прогресса, расхождение устройств, откат через старое сохранение | Состояние в D1 |
| Нет миграций | Схему нельзя воспроизвести и откатить | `migrations/NNNN_*.sql` + `wrangler d1 migrations` |
| Версия в константах кода | Пост о релизе и уведомление в игре зависят от деплоя | Таблица `releases` + манифест `/api/release` |
| 8.5 тыс. строк в одном файле | Трудно поддерживать | Модули на TypeScript, сборка Vite |
| Pages без крона | Фоновые задачи зависят от того, заходят ли игроки | Worker с Cron Triggers |

## 2. Техническая архитектура

### 2.1. Стек

```
autocrew/
  src/shared/      игровые правила и каталоги (TypeScript, общие для сервера и клиента)
  src/worker/      Cloudflare Worker: API, бот, крон, админка
  src/client/      Mini App (Vite, без фреймворка или на Preact; canvas для пиксель-арта)
  migrations/      SQL-миграции D1
  content/         каталоги: машины, запчасти, поставщики, заказы, шаблоны событий (JSON, версия контента)
  tools/           баланс-симуляция, проверки
  tests/           юнит-тесты правил и интеграционные тесты API (vitest + miniflare)
```

- **Cloudflare Worker + Static Assets** вместо Pages: один деплой отдаёт и клиент, и API, и поддерживает Cron Triggers (новости, события, итоги дня).
- **D1**: всё состояние игроков, журнал операций, новости, события, публикации, релизы.
- **R2**: не нужен до появления пользовательских картинок или больших бэкапов. Бэкапы D1 закрываются встроенным Time Travel (восстановление на момент времени) и еженедельным `wrangler d1 export` в CI.
- **Claude API**: только в News Engine, вызывается из крона, вход недоверенный, выход строгий JSON по схеме (раздел 7).

### 2.2. Сервер — источник истины

Клиент никогда не присылает «у меня столько-то денег». Он присылает **команду** («начать заказ #812 на посту 1», «купить в корзине у поставщика S2»). Сервер:

1. проверяет подпись initData и `auth_date`;
2. загружает компанию игрока;
3. **догоняет мир до текущего момента** (`advance(company, now)`): завершает ремонты, у которых истёк срок, принимает поставки, списывает суточные расходы, генерирует входящих клиентов. Генерация детерминирована: зерно случайности = `company_id + номер тика`, поэтому повторный расчёт даёт тот же результат;
4. проверяет команду по правилам из `src/shared`;
5. применяет изменения и пишет проводки в журнал одним `DB.batch` (в D1 это транзакция);
6. возвращает новое состояние (или разницу).

Офлайн-прогресс — это тот же `advance`, просто за больший промежуток.

### 2.3. Деньги и защита от повторов

- **Журнал проводок** `ledger`: каждая операция с деньгами — строка с суммой, статьёй (выручка, запчасти, аренда, зарплата, налог, кредит…) и ссылкой на источник. Баланс компании = сумма проводок; поле `companies.cash` — кэш, сверяемый с журналом в тестах и ночной проверкой.
- **Идемпотентность**: каждая команда несёт `op_id` (UUID, создаётся клиентом один раз на нажатие). Таблица `ops (company_id, op_id) PRIMARY KEY` хранит результат. Повтор того же `op_id` возвращает сохранённый ответ и ничего не применяет повторно.
- **Оптимистическая блокировка**: `companies.version` увеличивается при каждой записи; `UPDATE … WHERE version = ?` не даст двум параллельным запросам применить конфликтующие изменения.
- **Источники денег ограничены кодом**: деньги появляются только из оплаты заказа, продажи машины или детали, кредита, награды события из разрешённого шаблона, покупки за Stars. Других путей в коде нет.
- **Лимит запросов**: не больше 10 команд в секунду на игрока (счётчик в D1 или Rate Limiting binding).

### 2.4. Обновления клиента

- Сборка кладёт в ассеты `build.json` (`{version, build_id}`), а в таблицу `releases` при деплое из CI пишется запись релиза.
- Клиент раз в 2 минуты и при возврате в приложение запрашивает `/api/release`. Если `build_id` другой — показывает баннер «Вышло обновление AUTO CREW» с кнопками «Обновить игру», «Что нового?» и «Подробнее в Telegram».
- «Обновить» блокируется, пока в клиенте есть неотправленная команда (например, идёт торг или открыта корзина). Так как состояние на сервере, «сохранять» перед перезагрузкой нечего, нужно только дождаться ответа на отправленные команды. После перезагрузки клиент получает состояние с сервера; повторно отправленные команды отсекаются по `op_id`.
- Если `min_supported` выше версии клиента — сервер отвечает `426`, и клиент показывает обязательное обновление.
- Контентные обновления (события, заказы, предложения) идут через данные, перезагрузка не нужна.

## 3. Прогрессия: от пустого гаража до AUTO CREW PRIME

Ступень открывается только при выполнении **всех** условий: деньги на переход плюс резерв на неделю расходов, репутация, число выполненных заказов, а с ступени 3 ещё и нанятые специалисты и купленное оборудование. Пороги заказов и репутации стоят на уровне 85% от того, что активный игрок набирает к целевому дню. Поэтому несколько удачных сделок не дают перепрыгнуть ступень.

|---|---|---|---|---|---|---|
| 0 | Пустой гараж | старт | — | — | — | Название мастерской, покупка стартовых инструментов, объявления, заказы ТО: масло, фильтры, свечи, лампы |
| 1 | Оборудованный гараж | день 3 / 3 | 30 000 ₽ | 15 | 8 | Компрессор, подставки, набор головок; колодки, аккумуляторы, стойки стабилизатора; первый поставщик с доставкой |
| 2 | Первый механик | день 9 / 10 | 15 000 ₽ | 45 | 30 | Найм (объявление, кандидаты, собеседование), второе место в гараже, офлайн-работа 8 ч |
| 3 | Мастерская на 3 поста | день 23 / 32 | 120 000 ₽ | 125 | 140 | Аренда бокса, подъёмник, диагностика (сканер), ходовая, тормоза, шиномонтаж; поставщики с оптом |
| 4 | Автосервис на 5 постов | день 51 / 71 | 650 000 ₽ | 260 | 490 | Двигатель, КПП, автоэлектрика; мастер-приёмщик, закупщик; склад, кредиты |

«Казуальный» — заходит примерно 4 дня из 7. Разрыв небольшой, потому что с появлением сотрудников бизнес работает и без игрока; это сознательное решение, чтобы игра не наказывала за пропуски.

Отдельные направления на ступенях 6–8 открываются не деньгами, а набором условий. Пример — кузовной и покрасочный цех: помещение с вытяжкой (аренда +18 000 ₽/сут), покрасочная камера (1,6 млн ₽), стапель (900 тыс. ₽), кузовщик и маляр с навыком не ниже 50, запас материалов. Без любого пункта цех не запускается.

## 4. Экономическая модель

### 4.1. Время

- Работы измеряются в **норма-часах** (н/ч), как в реальных сервисах. 1 н/ч = **2 реальные минуты** работы поста. Замена масла (0,5 н/ч) идёт 1 минуту, снятие двигателя (8 н/ч) — 16 минут.
- **Сутки бизнеса = реальные сутки** по московскому времени. В полночь сервер списывает аренду, коммунальные, зарплаты и закрывает финансовый день.
- Владелец работает руками, только пока игра открыта. Персонал работает по графику смены, без управляющего — до 8 часов после последнего захода (офлайн-окно), с управляющим — постоянно. Расходы списываются всегда, поэтому бесконечного накопления при отсутствии нет.

### 4.2. Базовые значения

| Параметр | Значение | Обоснование |
|---|---|---|
| Стартовый капитал | 60 000 ₽ | ~28 000 ₽ уходит на обязательный набор (ключи, домкрат, съёмник фильтров, лампа, расходники), остаётся на 2–3 недели аренды гаража |
| Аренда гаража + коммунальные | 850 ₽/сут | ~25 000 ₽/мес за гараж в кооперативе |
| Ставка н/ч | 1 200 → 1 500 → 1 900 → 2 300 → 2 500 → 2 900 → 3 300 ₽ | Растёт с оборудованием и репутацией; премиальные работы до 8 000 ₽ |
| Наценка на запчасти | 5% → 28% | Зависит от доступных поставщиков: розничный магазин даёт 5%, оптовый контракт 25–30% |
| Зарплата механика | 2 500–4 300 ₽/сут | 75–130 тыс. ₽/мес в зависимости от навыка |
| Налог | 6% выручки | Упрощённая система |
| Расходники | 4% от стоимости работ | Ветошь, очистители, перчатки |
| Претензии | ~6% заказов, снижается с навыком и оборудованием | Переделка за свой счёт и −8 репутации |
| Выработка механика | 7 н/ч за смену × эффективность 0,85 | Усталость, перекуры, простои |
| Перепродажа машины | ~6 дней оборота, средняя прибыль 70 000 ₽, в 18% случаев убыток ~90 000 ₽ | Скрытые дефекты и ошибки оценки делают риск реальным |

### 4.3. Спрос — главный ограничитель

Число клиентов в сутки = `min(вместимость, база ступени + репутация × k)` с разбросом ±15%. Клики не создают заказы: если клиентов нет, работать не над чем. Рост идёт через репутацию (качество, сроки, отсутствие претензий), рекламу (платная, со снижающейся отдачей) и новые виды работ.

Прирост репутации за заказ: `(+2,5 при успехе, −8 при претензии) × 60 / (60 + текущая репутация)`. Первые очки даются быстро, дальше каждое следующее требует всё больше работы.

### 4.4. Что не даёт экономике разогнаться

- Постоянные расходы растут вместе со ступенью, поэтому новая ступень сначала просаживает прибыль.
- Свои инструменты и оборудование изнашиваются; обслуживание — около 1% стоимости в неделю.
- Склад ограничен по площади; детали без движения дешевеют.
- Каждое направление требует оборотных денег (машины на площадке, склад запчастей).
- Кредиты: ставка 18–30% годовых, лимит зависит от выручки за 30 дней; просрочка бьёт по репутации у поставщиков.

### 4.5. Проверка моделью

`python3 tools/balance_sim.py` — день достижения каждой ступени и что её сдерживает. `--casual` — игрок, который заходит 4 дня из 7. `tools/balance_tune.py` пересчитывает стоимости и пороги, если поменять целевые сроки. Результаты (3 разных зерна случайности дают ±3 дня):

```
Активный:    3 · 9 · 23 · 51 · 80 · 131 · 211 · 318 дней
Казуальный:  3 · 10 · 32 · 71 · 111 · 161 · 240 · 347 дней
```

Ограничения модели, которые я закрою на этапе 4: ступени 5–8 в ней упрощены (направления и филиалы заданы средним доходом в сутки), не учтены кредиты и события. В модели во всех ступенях последним выполняется условие по деньгам, а репутация и заказы отстают от него на 15%.

## 5. Игровые системы

### 5.1. Заказ на ремонт (ядро MVP)

Клиент приезжает → игрок смотрит машину и жалобу → **осмотр** (бесплатно, 0,2 н/ч) показывает, что сломано; на ступени 3 диагностика сканером находит и скрытое → игрок составляет **смету** (работы по нормам + запчасти по розничной цене каталога) → клиент соглашается или уходит, если дорого → нужные детали: со склада, или заказ у поставщика (клиент ждёт, его терпение падает) → ремонт на посту (н/ч × 2 мин, качество зависит от навыка, инструмента и качества детали) → выдача и оплата → репутация.

Неправильная деталь (не та модификация двигателя) обнаруживается при установке. Бракованная деталь даёт поломку и претензию через 1–3 дня.

### 5.2. Запчасти и поставщики

- Каталог: тип детали × совместимость (платформа, двигатель, год) × производитель (оригинал / качественный аналог / дешёвый аналог).
- Поставщики (описаны в `content/suppliers.json`): ассортимент, коэффициент цены, качество (доля брака), минимальный заказ, срок и стоимость доставки, надёжность (вероятность задержки или недостачи), условия оплаты (предоплата / отсрочка 7–30 дней на высоких ступенях).
- Первый доступный — «Автомагазин у дома»: самовывоз 20 минут, цена 95% от розницы, ассортимент только расходники. Остальные открываются репутацией и ступенями.
- Поставки — реальные записи с датой доставки. Задержка, недостача, брак и возврат происходят на сервере по характеристикам поставщика, а не случайно сами по себе.

### 5.3. Персонал

Кандидаты генерируются из пула под объявление (платное, 1–3 дня). У каждого: специализация, навыки 0–100 по направлениям, опыт, ожидаемая зарплата, характер (аккуратный, быстрый, конфликтный, ненадёжный…). Собеседование — вопросы, ответы на которые подсказывают скрытые черты. Усталость растёт за смену и падает в выходные. Мотивация зависит от зарплаты относительно рынка, переработок и конфликтов. Производительность = навык × (1 − усталость) × мотивация. Навык растёт от выполненных работ. Конфликты между сотрудниками с несовместимыми характерами. Увольнение — выплата за 2 недели.

Профессии открываются по ступеням: механик (2), диагност и шиномонтажник (3), моторист, электрик, мастер-приёмщик, закупщик (4), продавец, оценщик, управляющий (5), кузовщик, маляр, разборщик, логист, бухгалтер (6), директор филиала (7).

### 5.4. Автомобили

- Модель машины в каталоге: марка (вымышленная, но узнаваемого класса, чтобы не копировать чужие бренды), поколение, кузов, модификации двигателя и КПП, комплектации, базовая цена, кривая амортизации, редкость.
- Экземпляр: год, пробег, история обслуживания, состояние 8 узлов (двигатель, КПП, подвеска, тормоза, кузов, электрика, салон, шины) в процентах, список скрытых дефектов.
- Рыночная цена = базовая × амортизация(возраст, пробег) × состояние × спрос на сегмент (сезон, события) × редкость.
- **Покупка**: продавец показывает «заявленное» состояние. Осмотр открывает часть правды, диагностика сканером — больше, разборка узла — всё. Торг зависит от характера продавца и найденных дефектов.

### 5.5. Направления ступени 6+

Каждое — отдельная сущность `business` со своим помещением, оборудованием, персоналом и отчётом:

- **Разборка** — покупает битые машины, разбирает за н/ч, детали со степенью износа идут на свой склад или в магазин.
- **Магазин запчастей** — продаёт со склада внешним покупателям и своим сервисам по внутренней цене.
- **Тюнинг** — модификации с совместимостью, влиянием на характеристики и стоимость, риском снижения надёжности.
- **Кузов и покраска** — восстанавливает кузов (главный фактор цены перепродажи битых машин).
- **Реставрация** — многоэтапные проекты на недели, поиск оригинальных деталей, итоговая цена зависит от оригинальности.
- **Аукционы** — лоты с таймером, ставки ботов-конкурентов, на ступени 8 — закрытые.

Связи: разборка → склад → сервисы; кузов и тюнинг → стоимость машин на площадке; магазин → выручка с остатков склада.

### 5.6. События (Event Engine)

Событие запускается только из **шаблона** (`content/event_templates.json`). Шаблон задаёт: тип (спрос, предложение, задание, редкая машина, сезон), допустимые параметры с диапазонами (например, `demand_multiplier: 1.05–1.35`, `duration_days: 3–14`), условия участия (минимальная ступень), формулу награды от выручки игрока (чтобы награда не ломала раннюю экономику), а также ограничения, например не больше 2 активных событий спроса одновременно.

Внутренние события (задержка поставки, болезнь механика, поломка оборудования, конкурент рядом) происходят из состояния: болезнь — от усталости, поломка — от износа, конкурент — от доли рынка в районе.

## 7. News Engine, канал и автоматизация

**Конвейер (крон каждые 30 минут)**: забрать RSS из включённых `news_sources` → отсечь старше 72 часов и дубликаты (`url_hash`, плюс похожесть заголовков) → сохранить → для новых статей вызвать Claude (классификация: тема, достоверность источника, интересность 0–100, применимость к шаблонам) → при оценке выше порога сохранить **предложение события**: только `template_id` из списка и параметры, которые сервер затем обрезает до диапазонов шаблона.

**Защита от инъекций**: текст статьи передаётся модели как данные в отдельном блоке с явным указанием, что инструкции внутри не выполняются. У модели нет инструментов, доступа к базе и секретам. Ответ проходит валидацию JSON-схемы; всё, что не соответствует, отбрасывается. Модель не может создать новый тип события, сменить цену или задать награду вне формулы шаблона.

**Режимы** (`admin_settings.automation_mode`):
- `MANUAL` — новости собираются, анализ и черновики только по кнопке;
- `REVIEW` (по умолчанию) — анализ и черновики автоматически, запуск событий и публикации — после одобрения админом;
- `AUTO` — автоматически запускаются только шаблоны и типы постов из белого списка, остальное как в REVIEW.

**Канал**: все посты проходят через `telegram_posts` (черновик → предпросмотр в боте админу с кнопками «Одобрить», «Изменить», «Отложить», «Отклонить» → публикация по расписанию → `message_id`). Ошибка отправки — до 5 попыток с нарастающей задержкой. Пост о релизе создаётся автоматически из `releases.notes`, поэтому придуманных обновлений не бывает: нет релиза — нет поста. Ссылка «Подробнее в Telegram» берётся из `message_id` этого поста.

**Админка**: страница `/admin` внутри Mini App, права проверяются на сервере по `admins`. Плюс команды в боте для быстрого одобрения.

## 9. Что нужно от вас перед этапом 3

1. **Где создать репозиторий**: предлагаю `staffvpn/autocrew`. Создание репозитория — внешнее действие, без вашего подтверждения его не делаю.
2. **Бот и канал**: есть ли уже бот и канал AUTO CREW? Токен и `CHANNEL_ID` задаются в секретах Cloudflare, в репозиторий не попадают.
3. **Аккаунт Cloudflare**: деплой из GitHub Actions требует `CLOUDFLARE_API_TOKEN` и `account_id` в секретах репозитория. До этого всё проверяется локально (`wrangler dev` + локальный D1).
4. **Сроки прогрессии**: целевые сроки (первый механик на 9-й день, PRIME примерно за 10–11 месяцев) устраивают? Модель пересчитывает стоимости под любые другие.
5. **Монетизация**: Brew Crew продаёт за Stars игровые деньги. Для AUTO CREW предлагаю **не продавать деньги и ступени**, иначе теряется смысл долгого пути. Допустимо: косметика (оформление гаража, покраска), второй слот офлайн-окна. Нужно ваше решение.
6. **Марки автомобилей**: предлагаю вымышленные марки с узнаваемыми классами, без реальных брендов и логотипов, чтобы не было юридических рисков. Реальные названия возможны только в новостях со ссылкой на источник.
